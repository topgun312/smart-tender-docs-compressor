# Логика решения и алгоритм

Данный файл описывает, как работает сервис Smart Tender Docs Compressor:
какая задача решается, из каких этапов состоит обработка, как устроен
алгоритм извлечения текста и как формируется итоговый результат.

## 1. Задача

Пользователь загружает PDF с конкурсной документацией госзакупки. Сервис
должен выделить из документа ключевые условия контракта и вернуть их в виде
структурированного JSON:

- сумма контракта;
- даты: заключения, начала и окончания исполнения, общий срок работ;
- требования к исполнителю;
- штрафы и неустойки;
- обеспечение исполнения контракта (размер, способ, условия).

## 2. Общая схема

```
POST /summarize (PDF)
   │
   ▼
queue_pdf()          ── валидация → запись задачи → сохранение файла
   │
   ├──► ответ клиенту: 202 + {job_id}
   │
   └──► фоновая задача process_job(job_id)
              │
              ▼
        summarize_bytes()  ──► to_thread
              │                ├─ извлечение текста (pypdf)
              │                └─ OCR (tesseract), если скан
              ▼
        UnifiedLLMClient.chat()  ──► Ollama / OpenAI / Anthropic
              │
              ▼
        парсинг JSON → нормализация → сохранение результата
              │
              ▼
        удаление временного PDF

GET /jobs/{job_id}  ──► чтение статуса / результата из БД
```

Ключевая идея: **обработка вынесена из HTTP-обработчика в фон**. Эндпоинт
приёма файла отвечает мгновенно (код `202`), а тяжёлая работа (парсинг PDF,
OCR, запрос к LLM) выполняется асинхронно в отдельной фоновой задаче.
Клиент опрашивает статус через `GET /jobs/{job_id}`.

## 3. Алгоритм по этапам

### Этап 1. Приём файла — `POST /summarize` → `queue_pdf()`

1. Проверка расширения файла: только `.pdf` (иначе `HTTP 400`).
2. Чтение содержимого файла в память.
3. Создание записи задачи в SQLite (`store.create`) со статусом `pending`
   и уникальным `job_id`. В записи фиксируются параметры запроса:
   `model`, `provider`, `max_chars`, `max_pages`.
4. Сохранение PDF на диск: `data/uploads/<job_id>.pdf`.
5. Возврат клиенту `JobResponse` (статус `202`).
6. Регистрация фоновой задачи `process_job(job_id)` через
   `BackgroundTasks` FastAPI.

### Этап 2. Обработка задачи — `process_job(job_id)`

1. Статус задачи меняется на `processing`, прогресс — «Извлечение текста из PDF».
2. Файл читается с диска по пути `data/uploads/<job_id>.pdf`.
3. Вызывается `summarize_bytes(...)`.
4. Успех: статус `completed`, прогресс «Готово», в поле `result` кладётся
   JSON с выжимкой.
5. Ошибка: статус `failed`, в поле `error` — текст исключения.
6. В блоке `finally` временный PDF удаляется с диска
   (`unlink(missing_ok=True)`), чтобы не накапливать файлы.

### Этап 3. Извлечение текста — `_extract_and_ocr()`

Это синхронная CPU-работа, поэтому вызывается через `asyncio.to_thread`,
чтобы не блокировать event loop.

1. Первая попытка — **pypdf**: извлекается текстовый слой PDF
   (`extract_text_from_pdf`). Учитываются ограничения `max_pages`
   (сколько страниц с начала) и `max_chars` (общий лимит символов).
   Если PDF не читается — текст считается пустым.
2. Определяется количество страниц `page_count(data)`.
3. Эвристика «похож ли документ на скан» — `looks_scanned`:
   `len(текст) / количество_страниц < ocr_min_avg_chars` (по умолчанию 100).
   Мало текста на страницу → документ, скорее всего, изображения/скан.
4. Если документ похож на скан **и** включён `OCR_ENABLED`:
   - страницы рендерятся в изображения через **PyMuPDF** (dpi задаётся `OCR_DPI`);
   - текст распознаётся через **tesseract** (`OCR_LANG=rus+eng`);
   - распознанный текст заменяет пустой/скудный текст, выставляется флаг `ocr_used=True`.
   - Если OCR недоступен (tesseract не установлен / нет языковых пакетов),
     но обычный текст уже извлечён — он используется как есть; если же текста
     нет вовсе — задача завершается ошибкой.
5. Если в итоге текста нет — поднимается `SummarizationError`
   («файл — скан без OCR»).

Возвращается кортеж `(document_text, ocr_used)`.

### Этап 4. Запрос к LLM — `summarize_bytes()`

1. Извлечённый текст оборачивается в промпты (`TENDER_SYSTEM_PROMPT`,
   `TENDER_USER_PROMPT`), требующие вернуть ответ строго в формате JSON.
2. Вызов `UnifiedLLMClient.chat(...)`:
   - провайдер определяется автоматически по имени модели
     (`claude*` → Anthropic, `gpt*`/`o1`/`o3` → OpenAI,
     `llama*`/`mistral`/`qwen*` → Ollama), либо задаётся явно через `provider`;
   - Ollama работает через OpenAI-совместимый интерфейс
     `http://<OLLAMA_BASE_URL>/v1`;
   - для платных провайдеров подсчитывается стоимость и токены.
3. Ошибка LLM перехватывается и превращается в `SummarizationError`.

### Этап 5. Парсинг и нормализация ответа

1. `_extract_json()` вытаскивает JSON из ответа модели:
   - снимает Markdown-обёртку (```json ... ```);
   - оставляет только подстроку от первой `{` до последней `}`;
   - пытается выполнить `json.loads`. Если это не удалось — возвращает `None`.
2. Если JSON не распарсился — возвращается `TenderSummaryResponse` с пустой
   выжимкой («не указано») и сырым текстом ответа в поле `raw_text`
   (чтобы клиент не потерял данные).
3. Если JSON распарсился — `_normalize_summary()` заполняет `TenderSummary`,
   подставляя значения по умолчанию для отсутствующих полей:
   - строковые поля (даты, суммы, сроки) — `"не указано"`;
   - списки (требования, штрафы, условия обеспечения) — пустой список `[]`.

### Этап 6. Получение результата — `GET /jobs/{job_id}`

`GET /jobs/{job_id}` читает запись задачи из SQLite и возвращает:

| status        | значение                                                    |
|---------------|-------------------------------------------------------------|
| `pending`     | задача создана, обработка ещё не началась                   |
| `processing`  | идёт извлечение текста / запрос к LLM                       |
| `completed`   | обработка завершена, результат в `result.summary`           |
| `failed`      | ошибка, причина в `error`                                   |

## 4. Состояния задачи (state machine)

```
pending ──► processing ──► completed
              │
              ▼
            failed        (при любой ошибке)
```

Особые случаи:

- **Перезапуск сервера.** При старте `lifespan` вызывает `store.fail_stale()`:
  задачи, «зависшие» в `processing` (обработка была прервана), помечаются
  как `failed` с сообщением «Обработка прервана перезапуском сервера».
- **Срок хранения.** Задачи старше `JOB_TTL_HOURS` (по умолчанию 24 ч)
  удаляются из БД при очередном обращении к списку задач (см. `store.cleanup`).

## 5. Хранение данных

- **SQLite** (`data/jobs.db`) — таблица `jobs`: статус, даты, имя файла,
  параметры, прогресс, результат (`result`, сериализованный JSON),
  ошибка (`error`).
- **Файловая система** (`data/uploads/<job_id>.pdf`) — временное хранение
  загруженного PDF, файл удаляется после обработки.

## 6. Ограничения и защита

- Принимаются только файлы `.pdf`.
- `max_chars` ограничен диапазоном 1000–200000 — защита от переполнения
  контекста LLM.
- `max_pages` ограничен 1–500 — защита от гигантских документов.
- `max_chars` / `max_pages` применяются и при извлечении текста, и при OCR.
- Тяжёлая CPU-работа выполняется в отдельных потоках (`asyncio.to_thread`),
  поэтому event loop остаётся отзывчивым.

## 7. Поток данных (что куда передаётся)

```
UploadFile (PDF)
   → bytes (data)
   → файл на диск data/uploads/<job_id>.pdf
   → bytes (читаются воркером)
   → текст (pypdf) → при необходимости текст (OCR)
   → системный промпт + пользовательский промпт + текст документа
   → LLM (Ollama / OpenAI / Anthropic)
   → сырой ответ модели (текст)
   → _extract_json → dict → _normalize_summary → TenderSummary
   → TenderSummaryResponse → JSON → поле result в записи задачи
   → GET /jobs/{job_id} → JobResponse (клиенту)
```

## 8. Примечания по реализации

- **`asyncio.to_thread`** используется для блокирующей работы (pypdf,
  tesseract), чтобы не блокировать асинхронный сервер.
- **Единый LLM-клиент** (`UnifiedLLMClient`) абстрагирует три провайдера;
  новый провайдер (например, Groq) добавляется через OpenAI-совместимый
  интерфейс.
- **Фоновые задачи** выполняются в том же процессе через `BackgroundTasks`
  FastAPI — отдельный воркер и опрос БД не используются, что снижает
  нагрузку на SQLite.
- Формат и правила заполнения выжимки задаются в `src/utils/prompts.py`;
  при изменении схемы ответа нужно синхронно менять и `TenderSummary`
  в `src/schemas/summary.py`.
